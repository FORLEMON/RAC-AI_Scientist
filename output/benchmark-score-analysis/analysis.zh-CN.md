**2. ResearchClawBench：按论文复现 checklist 给部分分，再加权平均**

本仓库锁定 revision 为 `ed664513287a1fc60ae319e6bf7dbe7a62144135`。已读取对应 [官方 evaluation/score.py](https://github.com/InternScience/ResearchClawBench/blob/ed664513287a1fc60ae319e6bf7dbe7a62144135/evaluation/score.py)，本地副本为 `tmp/benchmark-analysis/researchclawbench-score.py`，SHA-256 见审计 JSON。

评分器读取报告和隐藏 checklist；文字条目由 judge 阅读报告评估，图像条目还会比较生成图与参考图。每个条目是 0–100 的整数分，然后计算：

`总分 = Σ(条目权重 × 条目分数) / Σ条目权重`

其 rubric 把约 50 分定义为达到参考论文水平，而不是“做对一半问题”。不同条目分别覆盖结果、方法、分析或图表，可以获得部分分。一个条目差不会像乘法那样自动抹去其余条目的分数。评分器本身主要审阅产物，不直接执行提交代码验证所有结论。[官方评分源码](https://github.com/InternScience/ResearchClawBench/blob/ed664513287a1fc60ae319e6bf7dbe7a62144135/evaluation/score.py)

因此，更完整的证据、正确的结果解释和改进图表，可能在多个 checklist 条目上累积增益。不过，报告更长本身不是加分理由；是否解释了你观察到的历史 R3 增益，仍需查看那批逐条 judge 结果。

**3. DiscoveryBench：假设与参考答案的匹配度，是乘法评分**

当前提交入口是 `discovery_result.json` 中的 `hypothesis` 与 `workflow`。报告、图表和代码用于审计，不直接作为这条评分路径的完整研究报告来逐项打分。workflow 会进入 judge 的提示，帮助拆分和比较，但没有单独的“代码正确性分”或“工作量分”。

锁定的 [上游 new_eval.py](https://github.com/allenai/discoverybench/blob/c31fcf011e070f021a5f5b906896d0821f6880e8/eval/new_eval.py) 先拆分参考与预测假设，再按上下文逐个贪心配对；每个参考子假设最多匹配一次。对匹配项，变量按集合 F1 计算，关系按“很相似/相似但更笼统/不同”得到 1、0.5、0。

令 G 为参考子假设数，P 为预测子假设数，M 为匹配数，则当前实现的公式是：

`变量 F1 = 2 × 共同变量数 / (参考变量数 + 预测变量数)`

`最终分 = (M/G) × [Σ(上下文分 × 变量 F1 × 关系分) / P]`

这里有三个特别容易误解的地方：

- 关系分为 0 时，该匹配项整体为 0，其他方面做得好也不能补回来。
- 分母是所有预测子假设数 P。多写了没有对应参考的主张，即使是有意义的探索，也可能拉低分数。
- 加入额外变量可能降低变量 F1。此指标衡量与参考发现的一致性，不是对全部科学工作的综合评分。0.218182 不表示“21.8% 的分析正确”。

这次五个有效分数的完整分解如下；均已从原始 score.json 独立复算一致：

| Host / 条件 | G | P | M | 上下文召回 M/G | 匹配项变量 F1 | 匹配项关系分 | 总分 |
|---|---:|---:|---:|---:|---|---|---:|
| Evo N0 | 2 | 6 | 2 | 1 | 0.5000、0.5455 | 0、0 | 0 |
| Evo R3 | 2 | 5 | 2 | 1 | 0.5455、0.5455 | 1、1 | 0.218182 |
| Agent N0 | 2 | 5 | 2 | 1 | 0.5455、0.5455 | 0、0 | 0 |
| Agent R1 | 2 | 4 | 1 | 0.5 | 0.8571 | 1 | 0.107143 |
| Agent R3 | 2 | 5 | 2 | 1 | 0.5455、0.5455 | 0、0 | 0 |

Evo R3 的两个关系其实都得了满分，但参考变量数是 3、预测变量数是 8，交集为 3，故 F1 = 6/11；又被拆成 5 个预测子假设，最后为 `1 × (6/11 + 6/11) / 5 = 0.218182`。即使变量 F1 也满分，在 G=2、P=5 且两个参考均匹配时，当前公式最高也只有 0.4。

Agent R1 是 `0.5 × (6/7) / 4 = 0.107143`。所以它的低分不等于核心方向全部错误，而是匹配召回及额外子假设分母共同压低了总分。

**4. 输入和参考数据没有拿错；Agent R3 的负号需要结合变量编码理解**

六项输入 CSV 的 SHA-256 都是 `8a85ad04997555dd31e958e1562caf0674cfe052c51f63960976ead38dbf219e`，与 prepared task 相同。数据共有 12,686 行、9 列。

我用独立的 NumPy 最小二乘实现复算 `BMI ~ 截距 + DISSAVED + SAMESAVE`，得到：

| 变量 | 独立复算系数 | 参考答案系数 |
|---|---:|---:|
| DISSAVED | +0.3596215112 | +0.3596 |
| SAMESAVE | +0.4857966866 | +0.4858 |

因此，至少本题原始参考 OLS 的数据、方向和数值可以复现。还检查了原始分组：

| DISSAVED | SAMESAVE | 人数 | 平均 BMI |
|---:|---:|---:|---:|
| 0 | 0 | 4,913 | 24.8910 |
| 0 | 1 | 4,785 | 25.3768 |
| 1 | 0 | 2,988 | 25.2506 |

Agent R3 的分析代码第 57 行定义了 `future_oriented = 1 if DISSAVED == 0 and SAMESAVE == 0 else 0`。也就是说，它把另外两组聚合成一组，改用相反方向的指标：值越大表示它所定义的“未来导向”越强。

独立复算它的控制模型 `BMI ~ future_oriented + income + age + gender + black + hispanic`，得到 `future_oriented = -0.4312807132`，与提交中的 -0.431 一致。原代码标准化了 income 和 age；对这些协变量做线性缩放不会改变 future_oriented 的系数。

“未来导向更强的人 BMI 更低”在方向上可以与“DISSAVED/SAMESAVE 对应更高 BMI”一致。不能只看到负号就说它科学结论完全反了。与此同时，聚合指标也不等价于分别估计两个原始变量的效应，不能说它已完整复现参考答案。

问题出在提交又把这句话写成“time preference—proxied by DISSAVED and SAMESAVE—is negatively associated with BMI”，混用了原始时间偏好与反向编码的未来导向。judge 的两个关系判定都认为方向相反，给了 0。这里同时存在提交表达/变量定义不清、没有分别交付两个效应，以及 judge 对反向编码不够稳健的问题。

这次独立复算只验证了上述 OLS 系数，没有验证所有 bootstrap、p 值、中介效应、图表或因果解释。单次横截面分析的结果也不能仅凭这段提交就升级为因果结论。

**5. 另外几项为什么是 0 或低分**

Evo N0 的提交包含正的平均 OLS 系数，但主要强调低 BMI 分位为负、高分位为正的分布异质性，以及“不是统一上移”。judge 在理由中承认它含有正平均效应，但仍将整体关系判为不同。平均正相关与异质性并不必然矛盾；这个 0 不能证明它没有发现参考关系，也不证明它的扩展分析已经正确。

Agent N0 改用综合的时间偏好指标，突出非线性与分位变化，还出现“高 BMI 处效应更强”与负趋势数值并列的表述。judge 因此认为它没有保留两个原始变量分别正相关的关系。其代码对 SAMESAVE 的解释也有混乱：将它描述为持续储蓄/未来导向，而输入元数据的含义是储蓄不变或没有储蓄。这里存在实际的变量理解和叙述问题，不能全部归咎于评分器。

Agent R1 明确写了 DISSAVED 与 SAMESAVE 的正方向，却只匹配到一个参考子假设。其两个参考上下文完全相同，两个对应预测上下文也完全相同，但一个被匹配，另一个未匹配。上下文提示还包含假设文本，故这提示上下文匹配可能受到关系内容干扰；目前日志不保留每次失败匹配的原始回答，无法进一步分清单次 judge 波动和具体判断依据。

Evo R1 没有最终有效提交，其分数必须留空。工作目录 `outputs/` 下的中间 JSON 不能替代规定根目录的最终提交。它反映了运行/交付问题，不能用一个虚构的 0 与其他条件比较科学质量。

**6. 评分源码确实还有实现层面的疑点，不能只看最终总分**

最重要的一处在 `upstreams/discoverybench/eval/new_eval.py:423`：代码虽然遍历 `P_i ↔ G_j` 的匹配，却把完整的 `gold_hypo/gold_workflow/gen_hypo/gen_workflow` 传入变量与关系比较，而非该对子假设文本。注释描述的是对子假设逐项评估，实际参数却是全文。

这不是推测：五份有效 score.json 中，各配对记录的 HypoA/HypoB 都与完整假设相同；静态 AST 检查也确认了参数。因此，一个扩展结论或含混负号会反复影响多个配对。评分还会在各次配对中重复统计全文变量，使额外控制变量影响每一项 F1。可将其标为“上游实现与注释意图不一致、疑似实现缺陷”，但不能不声明版本就修改它并覆盖官方口径的原分数。

另一个例子是 Agent R3 的第二个匹配实际把“income 与 future orientation 正相关”的预测子假设配给了 SAMESAVE 与 BMI 的参考项，因为匹配阶段主要按 context 贪心选择。随后关系阶段又比较全文，掩盖了配对本身的语义差异。这说明不能简单把 M=2 读成“两条参考发现都找对了”。

本仓库 adapter 没有另造加总公式：它装载锁定上游的函数定义。当前 `scoring.py`、`policy.py` 与本次运行冻结源码的 SHA-256 完全一致，上游 scorer 的 LF 规范化 SHA-256 也与记录吻合。因此本次审计看到的是实际运行逻辑。

但“保留上游函数/公式”不等于逐参数复现原作者实验：上游入口默认 judge 是 gpt-4-1106-preview，本次用 gpt-5.4；上游 facet helper 把输出上限固定为 250，而 adapter 遵循调用端的 512。拆分及上下文路径默认 temperature=1、上限 4096，与上游 helper 一致；变量/关系路径请求 temperature=0。不能把当前分数直接与使用原 judge 的论文数字比较，也不能在未做对照前声称换 judge 导致了多少降分。

当前 adapter 会拒绝空、截断、拒答或无效 facet 响应，不会把这些 provider 错误悄悄变成有效 0。这里的三个有效零分都有正常关系判断及理由，属于评分结果本身，不是 Excel/导出缺失值变成 0。

**7. 现在的 R3 为什么没有保证更高分**

`src/rac_ai_scientist/policy.py:194` 的 verifier 主要检查文件是否改变、输出是否非空、最终提交是否合法。它没有检查统计方向、变量编码、报告系数与代码输出是否一致，也没有独立重算模型。`supported` 的含义是“这些 contract 证据检查通过”，不是“研究结论被科学验证”。

Agent R3 的七次验证全部 supported，但最终为 0，这两者并不矛盾。Agent R1 与 R3 实际上都执行相同的七个阶段：文献、计划、数据准备、实验、结果解释、报告写作、报告修订。R3 增加 contract/advisory context，并不意味着每次都改走另一条研究路线。

代码优先选择未完成的 native requirement；verifier 的结论是 advisory，本身不能触发停止、重试、改路或回滚。这也是交接文档明确约定的 R3 语义，而非本次临时出现的问题。增强科学证据检查时应保持这一语义，不能把强制纠错控制流偷偷加进 R3 后仍称为同一个条件。

Evo R3 确实经历了两次 debug 验证 refuted，之后仍进入分析和写作。这说明它有额外的协调和调试过程，但仅凭存在这些过程，并不能推出最终目标指标必然单调上升。

**8. 运行成本、故障与单任务限制，也会影响比较**

各条件共享 USD 40、900 次调用、6 小时、相同 token 上限；R1/R3 的 max_hops 为 8。共同预算上限允许算法消耗不同资源，这是合法的共同预算比较；但它不等于实际调用量或成本相等。N0 走完整原生 lifecycle，R1/R3 走分阶段 RAC loop，调用粒度也不同。

Evo R3 使用了 446 次调用，而 N0 是 41 次，相差约 10.9 倍，保守费用约 15 倍。它的分数提高可以如实报告，但不能据此声称在相同实际计算量下更有效。Agent R1 与 R3 调用量相近，实际输出 token、错误和耗时仍不同。

|---|---:|---:|---:|
| Evo N0 | 21 | 4 | 0 |

这里是外部运行请求，不是模型调用，也不是独立实验失败率；请求可能是依赖安装、文件操作或分析命令。日志出现缺包、变量未定义、路径错误、语法错误、奇异矩阵与超时。它们说明部分时间和预算用于解决执行问题；不能仅凭 CPU 低或模型调用数就判断主要时间花在哪里。

最后，每个条件只有一个任务和一次 seed。这里的 seed 标签也不等于模型响应或 judge 完全确定。不能据此估计总体方差、显著性，或断言 R3 跨 benchmark 必然优于 N0。即使第一套 benchmark 的历史增益成立，换研究任务、评分目标、host 或预算后，也需要重新验证。

**9. CORE-Bench 的分数也不同，补充避免混淆**

当前 CORE-Bench 使用锁定 HAL scorer `upstreams/hal_harness/hal/benchmarks/corebench.py`，不通过上述 LLM judge 给研究报告打分。它对 `report.json` 的结构化答案进行程序检查：数值答案落在参考重复运行得到的 95% 预测区间内算正确；列表直接比较；字符串忽略大小写比较。

它的顶层 accuracy 是“一个 capsule 的所有问题是否全对”后再按任务平均。当前只选一个 capsule 时，顶层分数通常是 0 或 1；答对部分问题会留在 correct_written_answers / correct_vision_answers 等计数中，不等于获得同等比例的顶层分数。预测区间也不是固定的 ±5% 容差。

所以三者分别是：ResearchClawBench 的 checklist 加权质量分、DiscoveryBench 的参考假设匹配分、CORE-Bench 的整任务全对率。把它们都缩放到 0–100，也不能当成同一把尺子。

**10. 建议下一步按这个顺序处理；本次尚未实施**

1. **先审计评估本身。** 保留五份原始分数及 Evo R1 的空值。固定现有提交，补齐每次 context 判断与原始 judge 请求/响应记录；如需重复评分或比较 judge，应另列诊断结果及版本、记录费用。对子假设传参的修正应独立标为修订指标，不能覆盖原上游口径。
2. **统一所有条件的提交表达。** 从公开任务要求出发，明确变量名、编码、参照组、方向、估计量与不确定性。核心回答和扩展探索分开，完整探索保留在报告/输出中；所有条件收到同一契约。不能把隐藏答案或此次审计得到的参考系数塞回 agent，亦不能只给 R3 特殊提示。
3. **增强 R3 的证据检查，但不改变其 advisory 语义。** 可让 verifier 检查“负系数是否对应反向编码”“提交系数是否存在于输出”“运行结果是否成功”“图表和文字是否一致”，把具体反证放入下一跳上下文。是否改动控制流应作为另一个明确命名的实验条件。
